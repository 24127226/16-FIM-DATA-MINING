\subsection{Experimental Setup and Measurement Protocol}
\label{subsec:exp_setup}

All official benchmarks were executed on a fixed reference machine (\texttt{results/ENV.md}): 11th Gen Intel Core i5-11400H (2.70~GHz, 12 hardware threads, 15.8~GiB RAM, Windows~x64), running Julia~1.11.4 (single-threaded) and OpenJDK~25.0.5.1 LTS for the SPMF reference binary (\texttt{spmf.jar}, Eclat~v2.65, SHA-256 prefix \texttt{bb371b99}).

Four canonical benchmark datasets from the FIMI and SPMF repositories (mirrored publicly on Hugging Face with SHA-256 verification) cover both dense and sparse regimes (Table~\ref{tab:b06_datasets}). Every dataset's measured statistics ($N$, $m$, $\bar{L}$) match the project specification table exactly, including the FIMI 8,124-transaction version of \texttt{mushroom}.

\textbf{Measurement Protocol:} Each dataset is evaluated across a locked 7-point descending \texttt{minsup} grid (\texttt{results/minsup\_grid.csv}). Every timing measurement runs inside a fresh operating-system process with 3 repetitions (reporting the median). Inside each Julia worker process, a warm-up run on \texttt{pasquier99.txt} precedes timing via \texttt{time\_ns()}, separating algorithm time (\texttt{t\_algo\_s}) from full process wall time (\texttt{t\_wall\_s}, which includes JIT or JVM startup). Internal instrumentation (\texttt{EclatStats}) is strictly disabled during timing runs and measured in a separate pass. Both \texttt{EclatFIM} and SPMF stream outputs to disk on the same drive.

\subsection{E2 \& E3: Runtime and Output Size Scaling with \texttt{minsup}}
\label{subsec:exp_e2_e3}

\textbf{Hypotheses (H2, H3, H8, H9):} Lowering \texttt{minsup} causes exponential growth in output size (especially on dense datasets); \texttt{v6} should substantially outperform \texttt{v0} and SPMF \texttt{Eclat} (which uses boxed \texttt{HashSet<Integer>}) and remain competitive with SPMF \texttt{Eclat\_bitset}.

\textbf{Results:} Figure~\ref{fig:f03_time} compares median algorithm runtime across all four benchmarks (\texttt{results/e2\_time.csv}), while Figure~\ref{fig:f04_itemsets} contrasts frequent itemset counts between dense and sparse regimes. At the lowest \texttt{minsup} of each grid:
\begin{itemize}
    \item \textbf{\texttt{chess} (65\%, 111,239 itemsets):} \texttt{v6} runs in \textbf{0.1046~s} vs.\ \texttt{v0} (0.8484~s, $8.1\times$ slower), SPMF \texttt{Eclat} (4.997~s, $47.8\times$ slower), and SPMF \texttt{Eclat\_bitset} (0.112~s).
    \item \textbf{\texttt{mushroom} (18\%, 57,413 itemsets):} \texttt{v6} runs in \textbf{0.0794~s} vs.\ \texttt{v0} (0.4709~s, $5.9\times$ slower), SPMF \texttt{Eclat} (1.209~s, $15.2\times$ slower), and SPMF \texttt{Eclat\_bitset} (0.093~s).
    \item \textbf{\texttt{retail} (0.1\%, 7,589 itemsets):} \texttt{v6} runs in \textbf{0.1823~s} vs.\ \texttt{v0} (5.543~s, $30.4\times$ slower), SPMF \texttt{Eclat} (0.804~s, $4.4\times$ slower), and SPMF \texttt{Eclat\_bitset} (0.654~s, $3.6\times$ slower).
    \item \textbf{\texttt{T10I4D100K} (0.2\%, 13,255 itemsets):} \texttt{v6} runs in \textbf{0.1955~s} vs.\ \texttt{v0} (2.6044~s, $13.3\times$ slower), SPMF \texttt{Eclat} (0.752~s, $3.8\times$ slower), and SPMF \texttt{Eclat\_bitset} (0.247~s).
\end{itemize}

\textbf{Explanation:} On dense datasets, 64-bit SIMD \texttt{BitVector} intersections in \texttt{v6} achieve $O(N/64)$ cost per pair, crushing \texttt{HashSet}-based SPMF \texttt{Eclat} by $15\times$--$48\times$. On sparse \texttt{retail} ($m = 16{,}470$), the upper-triangular level-2 array eliminates almost all infrequent item pairs before any tidset intersection occurs, while hybrid switching avoids the $O(N/64)$ penalty of sparse bitsets—yielding a $30.4\times$ speedup over \texttt{v0} and $3.6\times$ over SPMF \texttt{Eclat\_bitset}. Notice also that for short runs ($< 0.2$~s), full process wall time (\texttt{t\_wall\_s} $\approx 3.2$~s for Julia vs.\ $\approx 0.4$~s for JVM) is dominated by Julia's first-invocation JIT startup (confirming H9).

\subsection{E4: Peak Memory Footprint at Median \texttt{minsup}}
\label{subsec:exp_e4}

\textbf{Hypothesis (H2, H7):} On dense datasets ($\rho > 1/32$), \texttt{BitVector} tidsets ($N/8$ bytes) occupy far less memory than \texttt{Vector\{Int32\}} ($4\sigma$ bytes); on sparse datasets ($\rho < 1/32$), \texttt{v6}'s hybrid rule retains compact vector tidsets and avoids bitset memory blowup.

\textbf{Results:} Figure~\ref{fig:f05_memory} reports peak live tidset bytes (\texttt{EclatStats}) and added process RSS above the 158.9~MiB Julia baseline at the median \texttt{minsup} level (\texttt{results/e4\_memory.csv}). On \texttt{chess} (80\%), peak live tidset memory drops by \textbf{$33.4\times$} (from 901.4~KiB in \texttt{v0} to 27.0~KiB in \texttt{v6}); on \texttt{mushroom} (35\%), it drops by \textbf{$23.1\times$} (from 1,168.9~KiB to 50.6~KiB). Conversely, on sparse \texttt{retail} (1%), SPMF \texttt{Eclat\_bitset} allocates 840.8~MiB of JVM heap for sparse bitsets, whereas \texttt{EclatFIM (v6)} stays in compact vector representation (826.0~KiB live tidsets, 120.8~MiB delta RSS).

\subsection{E5: Scalability on Nested Retail Subsets}
\label{subsec:exp_e5}

\textbf{Hypothesis (H4):} With relative \texttt{minsup} fixed ($0.2\%$), runtime should scale linearly with database size $N$ because tidset lengths grow proportionally to $N$ while the frequent pattern lattice remains nearly invariant.

\textbf{Results:} Figure~\ref{fig:f06_scalability} plots median runtime across nested subsets $10\% \subset 25\% \subset 50\% \subset 75\% \subset 100\%$ of \texttt{retail} (\texttt{results/e5\_scalability.csv}). Linear regression confirms strong linearity for \texttt{v0} ($R^2 = 0.9968$, 0.317~s $\to$ 1.771~s), SPMF \texttt{Eclat} ($R^2 = 0.9575$, 0.257~s $\to$ 0.685~s), and SPMF \texttt{Eclat\_bitset} ($R^2 = 0.9788$, 0.265~s $\to$ 0.633~s). For \texttt{v6}, runtime stays nearly flat between 0.119~s and 0.134~s ($R^2 = 0.5291$) because the optimized mining kernel executes in milliseconds and is dominated by fixed per-invocation overhead.

\subsection{E6: Impact of Average Transaction Length ($\bar{L}$)}
\label{subsec:exp_e6}

\textbf{Hypothesis (H5):} Increasing average transaction length $\bar{L}$ at fixed $N = 50{,}000$, $m = 1{,}000$, and \texttt{minsup} $= 1\%$ increases co-occurrence density and pattern depth, causing superlinear/exponential growth in output size and runtime (Zaki~\cite{zaki2000scalable}, Appendix~A).

\textbf{Results:} As target $\bar{L}$ increases from $5$ to $30$ (\texttt{results/e6\_tx\_length.csv}, Figure~\ref{fig:f07_txlen}), frequent itemsets expand $18.6\times$ (from 828 to 15,432) and maximum pattern length increases from 8 to 11. Runtime escalates $16.8\times$ for \texttt{v0} (0.241~s $\to$ 4.058~s) and $9.0\times$ for SPMF \texttt{Eclat} (0.148~s $\to$ 1.335~s). In contrast, \texttt{v6} remains highly resilient (0.1065~s $\to$ 0.1405~s, achieving a \textbf{$28.9\times$ speedup over \texttt{v0}} and \textbf{$9.5\times$ over SPMF \texttt{Eclat}} at $\bar{L} = 30$) due to level-2 triangular pruning, adaptive galloping, and zero-allocation buffer reuse.

\textbf{Concrete Future Optimization Proposals:}
\begin{enumerate}
    \item \textbf{Diffset Representation (dEclat~\cite{zaki2003fast}):} On ultra-dense datasets (e.g., \texttt{chess} at $\texttt{minsup} < 50\%$ or \texttt{accidents}), storing transaction differences $d(PX) = t(P) \setminus t(PX)$ shrinks set cardinalities dramatically as recursion deepens, reducing both intersection cost and memory footprint beyond \texttt{BitVector}.
    \item \textbf{Parallel Top-Level Equivalence Classes (\texttt{Threads.@spawn}):} Because prefix-based equivalence classes at depth~1 are completely independent (Zaki~\cite{zaki2000scalable}, §4.2), assigning each root class to a thread-local \texttt{Workspace} can deliver near-linear multi-core speedups on our 12-thread CPU with zero lock contention.
    \item \textbf{Eliminating Cold JIT Latency via \texttt{PrecompileTools.jl} / Sysimage:} E2 showed that Julia's $\approx 3$~s cold startup exceeds algorithm runtime on short workloads. Precompiling concrete workloads into a custom sysimage would bring wall time down to parity with JVM startup.
\end{enumerate}
